# Сравнение систем контроля версий: Git и SVN

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

**Git (Распределённая система):**
* В Git ветка — это просто **легковесный указатель** (ссылка) на определённый коммит (его хеш).
* При создании ветки Git не копирует файлы, а просто создаёт новый текстовый файл-ссылку размером около 40 байт.
* Поэтому создание, переключение и удаление веток происходит мгновенно, не требует ресурсов сервера и не занимает дискового пространства.

**SVN (Централизованная система):**
* В SVN концепция веток исторически реализована через **полное копирование директорий** на сервере.
* Хотя на уровне файловой системы сервера SVN использует оптимизацию (copy-on-write), логически и для клиента это выглядит как копирование всего дерева файлов.
* Создание ветки требует времени на обработку сервером, а история репозитория засоряется записями о копировании тысяч файлов.

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

**Нет, нельзя.**

* **Причина:** SVN — это *централизованная* система контроля версий (CVCS). В ней нет локальной полноценной копии репозитория с полной историей, как в Git.
* Локально у вас хранится только рабочая копия (working copy) файлов и служебная папка `.svn` с базовыми метаданными.
* Операция `commit` в SVN означает отправку ваших изменений на центральный сервер для создания новой глобальной ревизии. Без сетевого соединения с сервером эта операция физически невозможна. *(Вы можете редактировать файлы офлайн, но зафиксировать изменения в репозиторий без сети не получится).*

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

Несмотря на тотальное доминирование Git, SVN остаётся актуальным и даже предпочтительным в следующих нишах:

* **Работа с бинарными файлами:** Если проект состоит из больших бинарников (ассеты для игр, 3D-модели, PSD-файлы, скомпилированные библиотеки). Git плохо работает с бинарниками (раздувает размер репозитория, не умеет делать merge). SVN хранит бинарники эффективно и поддерживает **file locking** (блокировку файлов), чтобы два человека не редактировали один бинарный файл одновременно.
* **Строгая централизация и контроль доступа:** В корпоративных средах, где требуется жёсткий контроль. SVN позволяет «из коробки» настраивать права доступа на уровне отдельных директорий (например, дать доступ к папке `finance/` только бухгалтерии, а к `src/` только разработчикам). В Git репозиторий всегда клонируется целиком, и для ограничения доступа к папкам требуются сложные надстройки (Gitolite, серверные хуки).
* **Огромные монорепозитории с частичной загрузкой:** Если репозиторий весит сотни гигабайт, а разработчику нужна только одна конкретная папка. SVN изначально и нативно поддерживает *sparse checkouts* (загрузка только нужных подкаталогов). В Git это тоже появилось (`git sparse-checkout`), но в SVN это работает проще и прозрачнее для конечного пользователя.
* **Специфичные legacy-проекты:** Проекты, которые работают 15+ лет, где вся инфраструктура, CI/CD и привычки команды заточены под SVN, а стоимость миграции на Git превышает выгоды.
